# Bake API Without a Bake Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let a game say what is static, how each light takes part in baking, and which spaces and chunks get baked, and have the renderer work out every bake's input hash each frame. No bake exists yet, so nothing may look different: with no bake, every existing scene renders byte-identical to before.

**Architecture:** Rendition gains the data: `LightMode` on both light structs, `DrawItem.BakeId`, and `BakedSpace` and `BakedChunks` on `FrameView`. Pure static helpers in Rendition (`StableHasher`, `BakeIds`, `BakeAreas`, `BakeInputHash`) decide which area owns each draw and light and hash the inputs, so Super and Rendition share one rule. Super computes bake ids in `SceneRenderer.PrepareDraws` from content hashes, and offers `Static`, `isStatic`, `View.BakedLighting` and `View.BakedChunk`. Each frame `Renderer.Render` asks a `BakeFreshness` resolver which areas have a fresh bake. Plan 4's only store is `NoBakes`, which never has one, so every light stays Realtime and no light is dropped.

**Tech Stack:** C# (.NET 10), System.Numerics, System.IO.Hashing (XxHash64), xunit 2.9.

**Spec:** `docs/superpowers/specs/2026-11-11-lighting-design.md`, sections "What the developer writes", "Is the bake fresh?", Order step 4 and "How it's tested". Roadmap row 4 in `docs/superpowers/plans/2026-11-11-lighting-roadmap.md`.

## Global Constraints

- This plan depends on no other lighting plan and can run beside plans 2 and 3. Task 9 alone waits for plan 2 (lightmap UVs) to merge.
- `DrawItem.BakeId` is a `ulong` and zero means "not static". `LightMode` defaults to `Mixed`, so the enum's zero value is `Mixed`. Later plans rely on both.
- A missing bake changes nothing. Until plan 5 adds a store, no frame drops a light, changes a draw or touches the GPU differently. Every task keeps the existing examples byte-identical, and Task 8 proves it.
- Hashes are stable: the same inputs give the same `ulong` across runs, machines, cultures and draw order. Never use `HashCode` or `string.GetHashCode` for them, because both are seeded per process. Floats are hashed as their bits after rounding, never as text.
- Validation errors throw `ArgumentException` or `InvalidOperationException` with a message that names the value and the limit, formatted with `CultureInfo.InvariantCulture`, the way `View.LightProbes` does.
- Braces on every control statement. Conventional commits, no Co-Authored-By lines. Docs change in the same commit as the code: user-facing API in `docs/views.md` and `docs/rendering.md`, file paths in `docs/content.md`, hashing and membership in `docs/design.md`. Search `docs/` for each name you touch before committing.
- Rebuild before trusting a test result; never `--no-build`.

## Review Focus

The spec's tests cover the happy paths. These five input classes are not covered there; each has a test in the named task.

1. A chunk placed far from the origin and rotated (at (400, 0, -300), 37° about Y) must give the same bake ids and the same chunk hash as at the origin. Float error in `inverse(chunk) * draw` is the risk. Task 5 (`Chunk_far_from_the_origin_gives_the_same_bake_ids`) and Task 6 (`Chunk_hash_is_the_same_wherever_the_chunk_is_placed`).
2. Hashing under a culture with a comma decimal separator (`sv-SE`) must give the same hash as under the invariant culture. Task 6 (`Input_hash_is_the_same_under_sv_SE`).
3. The same draws and lights submitted in a different order must hash the same. Task 6 (`Input_hash_ignores_draw_and_light_order`).
4. Two lights that share one key in a frame, which the view allows but the tracker can't tell apart. Both count as animated. Task 7 (`Two_lights_sharing_a_key_are_both_animated`).
5. A light that stops moving returns to the bake after one second of game time, not before, and a clock that jumps back (a state change) doesn't strand it. Task 7 (`Settled_light_returns_after_one_second_and_not_before`, `Clock_going_back_starts_over`).

## Calls made

1. `LightMode` lives in Rendition with `Mixed = 0` so a default struct is Mixed, as the roadmap requires. Super reuses the Rendition enum rather than mirroring it.
2. A bake id is the instance hash with its low 12 bits replaced by the part index, and bit 63 set so it is never zero. That caps a static model at 4,095 parts, which throws. It lets the renderer group a draw's parts back into one instance without a second field on `DrawItem`.
3. A draw's membership is decided per instance from the union of its parts' bounding spheres, not per part, so a model is never split between areas. A part with no detail record counts as the point at its origin.
4. The spec says a draw "in" a chunk belongs to it but not how much must be inside. A draw belongs to the first chunk whose box holds its sphere's centre. Overlap would let a neighbour chunk's draws leak into a chunk's hash and break "stable across placement". For the space, overlap counts, because the space's bake already includes every static draw as a blocker.
5. A light inside both the space and a chunk belongs to the space, to match draws. The sun belongs to the space when there is one and to nothing otherwise.
6. Transforms are rounded element by element to 1e-4 (0.1 mm for translation, and the same step for the rotation terms). Chunk-relative transforms are computed in double precision so a chunk far from the origin hashes the same.
7. Chunk transforms must be rigid (rotation and translation only). A scaled chunk would scale its lighting, which the spec doesn't describe, so it throws instead.
8. Hashes use XxHash64 from `System.IO.Hashing`, a new package on Rendition, because `HashCode` is randomised per process. Floats are hashed as rounded integers, so culture never enters.
9. A model's content identity is the cooked manifest's SHA-256 through a new `IContentFiles.HashOf`, whose default hashes the file; a built-in shape is its name; a code mesh is a hash of its vertices, indices and surface, computed once when it is added.
10. The environment's hash is computed from what `SetEnvironment` and the sky were given (bands, panels, turbidity, environment intensity), not from the renderer's version counter, which moves even when the same environment is set again.
11. The box of a space or chunk goes into `Settings`, and the chunk's name goes into no hash, because the name is already the folder and one chunk asset is placed under one name many times.
12. Hashes and the animated-light tracker run every frame that names a space or chunk, and not at all when it names none. That keeps every existing scene's frame path untouched.
13. The animated-light tracker runs on the frame's game time (`FrameView.Time`), not wall time, so tests and recordings are repeatable. When the clock goes back, as after a state change, the tracker starts over. A light settles after exactly one second (`>=`).
14. Lights are tracked by key; suns by their index in the frame. Two lights sharing a key in one frame are both treated as animated and logged once, since the tracker can't tell them apart.
15. The tracker logs to the renderer's `TextWriter`, `Console.Error` by default, as the upscaler messages already do.
16. Light hashes include the light's mode, so switching a light between Mixed and Baked makes the bake stale. Realtime lights are in no hash.
17. `BakeInputs` keeps four part hashes (draws, lights, environment, settings) and a combined one, so plan 5's stale log can name what changed without storing every input.
18. The quality setting is in the hash, so a Preview bake is stale for a Final check. Plan 5 decides which quality a frame checks against; plan 4 uses `Final`.
19. Static plus swim, or static plus a pose, throws in the view, and Rendition throws again for a bake id with bones or swim, so a raw `DrawItem` user gets the same rule.
20. Repeated chunk names are allowed in one frame, because one chunk asset can be placed several times.
21. A code mesh is "created static" by passing `isStatic: true` to `Content.Mesh` (Task 9), rather than unwrapping on its first static draw, which would re-upload mid-game and change the mesh's identity under the bake.
22. The byte-identical proof is three-fold: a GPU test that adds areas, ids and Baked lights to a scene with no store and compares bytes; a `git grep` showing that no example opts in; and a `cmp` of every example's screenshot against the merge base.
